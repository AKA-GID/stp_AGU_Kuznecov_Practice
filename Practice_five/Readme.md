# Практическая №5

## Тема: Наследование и принцип подстановки Лисков (LSP)

В этой работе расширяется класс `Book` классом `Ebook`. Также разбираются три типичных нарушения LSP: нарушение инвариантов, усиление предусловий и ослабление постусловий.

### Часть 1. Расширение `Ebook`

Создайте класс `Ebook`, наследующийся от `Book`. Электронная книга хранит URL и добавляет методы:

- `url()` — возвращает URL;
- `download()` — сообщает о начале загрузки;
- `description()` — дополняет описание книги URL.

Конструктор `Ebook` должен вызвать конструктор `Book` для инициализации названия, автора, года и количества страниц.

### Часть 2. Нарушение LSP №1: инварианты

Попробуйте добавить в `Ebook` метод:

```cpp
void clearTitle() {
    title_ = "";
}
```

1. Компилируется ли этот метод, когда `title_` объявлено как `private` в `Book`? Почему?
2. Что изменится, если сделать `title_` и `author_` защищёнными (`protected`)?
3. Запустите вариант с `clearTitle()` и опишите, как он нарушает инвариант `Book` о непустом названии.
4. Верните поля в `private`, удалите `clearTitle()` и используйте `updateTitle()`, сохраняющий проверку корректности.

Итоговая версия практической должна оставлять поля `title_` и `author_` закрытыми. В `Practice_five/Book.h` они остаются `private`, а `Ebook` не предоставляет способ обойти проверки базового класса.

### Часть 3. Нарушение LSP №2: предусловия

Рассмотрите вариант переопределения `updateTitle()`, который запрещает названия короче пяти символов:

```cpp
void Ebook::updateTitle(std::string new_title) {
    if (new_title.size() < 5) {
        throw std::invalid_argument("Title too short for an Ebook");
    }
    Book::updateTitle(new_title);
}
```

Сравните поведение `Book` и `Ebook` при вызове `updateTitle("1984")`.

1. Почему дополнительное ограничение нарушает LSP?
2. Будет ли клиент, работающий с `Book*` и вызывающий `updateTitle("1984")`, работать с объектом `Ebook`?
3. Исправьте метод так, чтобы он делегировал проверку базовому классу, либо удалите переопределение.

В итоговом коде `Ebook::updateTitle()` делегирует вызов `Book::updateTitle()` и не вводит более строгих требований.

### Часть 4. Нарушение LSP №3: постусловия

Рассмотрите реализацию, возвращающую только URL:

```cpp
std::string Ebook::description() const {
    return "[URL: " + url_ + "]";
}
```

1. Почему клиент, ожидающий название и автора в описании любой книги, может некорректно работать с `Ebook`?
2. Исправьте реализацию так, чтобы она сохраняла информацию базового описания и добавляла URL:

```cpp
std::string Ebook::description() const {
    return Book::description() + " [URL: " + url_ + "]";
}
```

Метод `Book::description()` объявлен `virtual`, а метод `Ebook::description()` — с `override`. Это необходимо, чтобы вызов через ссылку или указатель на `Book` действительно выбрал реализацию `Ebook`.

### Часть 5. Полиморфная проверка LSP

Добавьте свободную функцию:

```cpp
void print_description(const Book& book) {
    std::cout << book.description() << std::endl;
}
```

Вызовите её для объектов `Book` и `Ebook`.

1. Почему `print_description(ebook)` принимает `Ebook`, хотя параметр имеет тип `const Book&`?
2. Какое описание выведется для `Ebook` при виртуальном вызове?
3. Что произойдёт, если `Ebook::description()` возвращает только URL?

## Что реализовано в примере

- Конструктор, `url()`, `download()` и расширенное описание `Ebook`.
- Закрытые поля `Book` и отсутствие `clearTitle()`, чтобы сохранить инварианты.
- `updateTitle()` в `Ebook` делегирует базовому классу без усиления предусловий.
- Полиморфное описание с сохранением названия и автора.
- Демонстрация вызова `print_description()` для обоих типов и обработки некорректного пустого названия.

Исходные файлы: `Book.h`, `Book.cpp`, `ebook.h`, `ebook.cpp`, `main.cpp`.
